# Architecture

What the template actually ships, and how a request moves through it. Read
[`conventions.md`](conventions.md) for the rules that keep it this shape, and
[`adr/`](adr/) for why the non-obvious parts are non-obvious.

## The domain

One model and one enum:

- `App\Models\User` — `HasApiTokens`, `HasRoles`, `LogsActivity`, `Notifiable`,
  `PasskeyAuthenticatable`, `TwoFactorAuthenticatable`, plus `canAccessPanel()`,
  `isStaff()`, `hasStaffRole()` and `staffRoleNames()`.
- `App\Enums\StaffRole` — `super_admin`, `support`.

That is on purpose. Teams, tenancy and billing are a product's decisions, not a
template's — see [ADR 0006](adr/0006-single-user-domain.md).

## Two presentations

```
app/Models, app/Actions, app/Policies   the shared domain
app/Http/Controllers + resources/js     the product UI      (Inertia + React)
app/Filament                            the staff panel      (/admin)
```

**Product UI** — Inertia v3 renders React pages from `resources/js/pages`.
Routes are in [`routes/web.php`](../routes/web.php) (`/`, `/dashboard`, health)
and [`routes/settings.php`](../routes/settings.php)
(`/settings/{profile,security,appearance}`). `HandleInertiaRequests` shares props;
`HandleAppearance` carries the light/dark preference in an unencrypted cookie so
the first paint is right.

**Staff panel** — a Filament v5 panel at `/admin`, configured in
`AdminPanelProvider` (amber primary, resources auto-discovered from
`app/Filament/Resources`, Shield plugin). Entry is gated by
`User::canAccessPanel()`, which is `isStaff()`.

Both call the same Actions and the same Policies. A Filament resource that
answers an authorisation question differently from the product is the drift this
split exists to prevent.

## A request, end to end

1. **`AssignRequestId`** is prepended to the global stack. It puts an id on
   `Context`, and on the response as `X-Request-Id`.
2. Routing splits on the path. `web` middleware adds appearance handling and the
   Inertia bridge; `api/*` is stateless and authenticated with Sanctum tokens.
3. The controller resolves. Product controllers return `Inertia::render(...)`;
   API controllers extend `App\Http\Controllers\Api\V1\ApiController` and use its
   `ok()` / `noContent()` helpers.
4. **On failure**, `bootstrap/app.php` renders one envelope for anything under
   `api/*` — `{error: {status, message, errors, request_id}}` — mapping
   validation to 422, auth to 401, denial to 403 and missing models to 404. A
   500 hides its message unless `APP_DEBUG`. The `request_id` is the same one
   from step 1 and the same one in the logs.

## Auth

Fortify, configured in `FortifyServiceProvider`, with the redirect responses
overridden in `app/Http/Responses/` (`LoginResponse`, `RegisterResponse`,
`TwoFactorLoginResponse`, `PasskeyLoginResponse`, `VerifyEmailResponse`).

- Password login, registration, reset, email verification.
- **Two-factor** — TOTP with recovery codes, at `/settings/security`.
- **Passkeys** — `@laravel/passkeys` (WebAuthn), same page, with a
  `.well-known/passkey-endpoints` route pointing browsers at it.
- `/settings/security` sits behind `RequirePassword`; password updates are
  throttled at `6,1`.
- **API** — Sanctum personal access tokens. There is no token UI; mint one in
  tinker.

Emails are `citext` in Postgres, so `Foo@Example.com` and `foo@example.com` are
the same account at the database level rather than only in validation.

## Authorization

Three layers, all resolving to the same place:

| Layer           | Where                                                                             |
| --------------- | --------------------------------------------------------------------------------- |
| Permissions     | Generated by Filament Shield, one per resource action                             |
| Policies        | `UserPolicy`, `RolePolicy` — check Shield's names as strings                      |
| Dashboard gates | `viewPulse`, `viewApiDocs` (`AppServiceProvider`), `viewHorizon`, `viewTelescope` |

Every gate is `$user?->isStaff()`. Laravel's bundled dashboards ship gates that
permit only the local environment, so without this they 403 everywhere else;
staff roles already describe who runs the product.

`RolesAndPermissionsSeeder` is infrastructure, not demo data — it invokes
`shield:generate`, grants `super_admin` everything and `support` the `View*`
subset, and is idempotent. Widen a role in Shield's UI at `/admin/shield/roles`,
not in code. See [ADR 0002](adr/0002-two-permission-vocabularies.md).

## Generated code

Two boundaries where PHP is the source of truth and the build fails if they
drift. Both outputs are gitignored.

- **Types** — `TypeScriptTransformerServiceProvider` emits `#[TypeScript]`-marked
  classes to `resources/js/types/generated.d.ts` as `App.Data.*` / `App.Enums.*`.
  `./keel ts` regenerates; `./keel types` regenerates and typechecks.
- **Routes** — Wayfinder generates `resources/js/{actions,routes,wayfinder}` from
  the route table at build time. Import the helper instead of writing a URL.

## Background work and health

`App\Jobs\BaseJob` implements `ShouldQueueAfterCommit` with sane retries and
backoff. Queues run on Redis, worked by Horizon (`/horizon`).

[`routes/console.php`](../routes/console.php) schedules three things, all health:
a scheduler heartbeat, a queue heartbeat, and a full check run every five
minutes.

`HealthServiceProvider` registers Database, Cache, Schedule (5-minute heartbeat),
Queue (`default`), and UsedDiskSpace (warn above 80%). Three more —
DebugMode, Environment, OptimizedApp — are skipped outside a deployed
environment, so a local `health:check` reports five.

`/up` is public and only proves PHP is executing. `/health` and `/health.json`
are behind `auth` + `can:viewPulse`, because the output describes your
infrastructure.

The queue and schedule checks fail when the `horizon` or `scheduler` Compose
services are not running. Sail ships neither, which is exactly why they are in
`compose.yaml` and in `KEEL_SERVICES` — see
[ADR 0005](adr/0005-pluggable-services.md).

## Runtime defaults

Set once in `AppServiceProvider::configureDefaults()`:

- `CarbonImmutable` for every date.
- `Model::shouldBeStrict()` outside production — lazy loading, missing attributes
  and mass-assignment mistakes throw immediately instead of failing quietly.
- `DB::prohibitDestructiveCommands()` in production.
- Strong `Password::defaults()` in production only, so local seeding and tests
  are not fighting a 12-character policy.

## Infrastructure

Docker Compose, one profile per optional service, driven by `KEEL_SERVICES` in
`.env` and exported as `COMPOSE_PROFILES` — `pgsql`, `redis`, `mailpit`,
`horizon`, `scheduler`, `pgweb`. `laravel.test` is always on.
[ADR 0005](adr/0005-pluggable-services.md) covers the design;
[ADR 0004](adr/0004-docker-only-bootstrap.md) covers why the first Composer
install happens in a throwaway container.

`stubs/` holds 57 published Laravel stubs so generated files carry
`declare(strict_types=1)` — the architecture test would otherwise fail on
everything you generate.
